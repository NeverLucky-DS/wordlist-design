## 0. Как это должно работать — и где рвётся

Продукт называется тренажёром эссе. Заявленный цикл читается из самих страниц:
человек **ищет слово** (Wörterbuch) → **кладёт его в свой список** → **пишет
эссе** (Schreiben), опираясь на этот словарь → **получает разбор** от модели →
**возвращается к словам**, которые не дались.

Ни одно из четырёх звеньев не соединено со следующим. Проверено грепом и на
живом стенде:

| звено | состояние |
|---|---|
| поиск → список | ✅ работает |
| список → письмо | ❌ `js/schreiben.js` содержит **ноль** обращений к `/api/vocab/*` |
| письмо → словарь | ❌ инструмент «Wörterbuch» в редакторе питается захардкоженным массивом `WORDS` (`schreiben.js:66-144`) — **12 слов, все про Technologie** |
| разбор → повторение | ❌ механизма повторения нет вовсе: греп `srs\|repetition\|review_at\|due_at\|interval\|ease` по `js/` и `backend/app` не даёт ни одного совпадения по смыслу |

Замер прямо в консоли живой `/schreiben.html`:

```
THEMEN_total   : 12
WORDS_total    : 12
themesWithWords: ["Technologie"]
```

На экране это выглядит так: `Technologie — 12 Wörter im Paket`, остальные
**одиннадцать тем — «Wortpaket folgt»**. То есть человек, севший писать эссе, в
11 случаях из 12 получает «словарь ещё не готов» — при **92 090 обогащённых
карточках**, лежащих за `/api/vocab/search` на соседней странице.

`user_word_list` (`backend/app/db/models.py:346`) хранит `lemma, ru, level, band,
pos, article, added_at`. Ни `review_at`, ни `interval`, ни счётчика ответов.
«Личный список слов на заучивание» — это закладки: он ничего не спрашивает и
никуда не ведёт.

**Вывод верхнего уровня.** Самая дорогая часть проекта уже построена и работает:
92 тысячи карточек, парадигмы на 69 % из них, честный поиск, аккуратный
акварельный интерфейс. Не построено дешёвое — четыре вызова API, которые
соединили бы это в продукт. Год работы вложен в склад, и он полон; не хватает
двери из склада в магазин.

Поэтому приоритет №1 ниже — не «улучшить словарь», а **соединить то, что уже
есть**. Всё остальное, включая качество данных, стоит после.

### 1.2. Словарь уверенно отвечает неправильно на самые частотные слова языка

Проверено запросами к живому `/api/vocab/search`, не рассуждением:

| запрос | zipf | что отвечает словарь |
|---|---|---|
| `ist` | **7.08** | `Ist-Wert` = фактическое значение |
| `hat` | 6.60 | `Hatz` = погоня |
| `sind` | 6.60 | `Sinn` = смысл |
| `war` | 6.53 | `warm` = тёплый |
| `wird` | 6.50 | `wir` = мы |
| `mir` | 6.32 | `Mir` = мир (ковёр) |
| `mich` | 6.26 | `Michelin-Männchen` = человечек Мишлен |
| `bin` | 6.10 | `Bingo` = бинго |
| `einen` | 6.48 | `einen` = объединять |
| `eine` | 6.80 | `einen` = объединять |

Это не «не нашлось» — это хуже. Карточки нет, честного «не найдено» тоже нет, и
триграммный поиск заполняет пустоту ближайшим мусором. Человек уровня B1,
ищущий `ist` — самую частотную спрягаемую форму немецкого языка, — получает
«фактическое значение» из технического словаря.

Замер по базе: **47 лемм с zipf ≥ 6.0** (это верхние 200–300 слов языка) сидят в
терминальных `failed`/`skipped` без карточки, и ещё 222 в полосе 5.0–6.0. Из 32
проверенных форм sein/haben/werden и личных местоимений: 18 `skipped`, 2
`failed`, done только четыре (`uns`, `dir`, `dich`, `euch`).

Причина ровно та же, что у §0b, и правило по-прежнему право: модель справедливо
отказывается делать `ist` отдельной карточкой, это форма `sein`. Но **`plan_repairs()`
не трогает `status='skipped'` вообще** (только `failed`), а механизм воскрешения
(`_annihilated_victims`) намеренно ограничен парами регистровых омографов — одиночная
словоформа его барьер не пройдёт никогда.

⚠️ Поэтому пункт 0b в PLANS.md помечен «✅ ЗАКРЫТО» преждевременно: закрыт список
из 25 слов, а не класс проблемы.

Чинится тем же приёмом, что и `funcwords.py`, — **руками, ноль токенов Mistral**:
презенс и претерит `sein`/`haben`/`werden`, полный датив и аккузатив личных
местоимений, склонение неопределённого артикля. Плюс отдельно пересудить карточку
`einen` = «объединять»: глагол настоящий, но на запрос `einen` человек почти
наверняка ищет артикль.

### 1.3. Закрыть остальные мутирующие ручки и поставить rate limiting

Три ручки уже закрыты в этой ветке (см. «Сделано»). Осталось то, что требует
твоего решения, потому что меняет продуктовое поведение:

**Анализ эссе доступен анонимному гостю и жжёт общий серверный ключ.**
`routes/essays.py:281-338` — `analyze_legacy` и `analyze_stream_legacy` без
защиты от параллельного запуска; `services/mistral_analyzer.py:613-614,643` —
используется `settings.mistral_api_key`, **один ключ владельца на всех**, а не
персональный ключ аккаунта (в отличие от обогащения, где ключ берётся из
`crypto.decrypt(user.mistral_key_enc)` для каждого аккаунта). Гостевая cookie
выдаётся автоматически, значит скрипт без cookie-jar получает новую сессию на
каждый запрос. `EssayCreate.text` (`schemas.py:8-14`) — без `max_length`.

**Rate limiting отсутствует полностью.** `grep -rln "ratelimit\|slowapi\|limits"
app/` → пусто; в `nginx.conf` ни одной директивы `limit_*`. Пароли хэшируются
корректно (`pwdlib[argon2]`), но перебор `POST /api/auth/login` ничем не
ограничен, как и регистрация одноразовых аккаунтов.

Минимум: `require_user` (не гость) на `/analyze*`, дневная квота, `max_length` на
текст, `limit_req` на `/api/auth/*`.

### 1.4. Бэкап Postgres — его нет вообще

`docker-compose.yml` держит данные в томе `pg_data`. Поиск по всему репозиторию
(`.py`/`.sh`/`Makefile`/`.yml`) на `pg_dump|pg_restore|restic|rclone|backup|cron`
не нашёл **ни одного** механизма.

Замер: том `wordlistdesign_pg_data` = 1.27 ГБ. Живой счёт: `users=17`,
`essays=4`, `user_word_list=10`. Это не производные данные — пересчитать их
неоткуда. При этом `make clean` (в Makefile прямо описан как «Stop the stack and
DELETE all data») стирает их одной командой без подтверждения.

Нужен `make backup-db` с `pg_dump` и напоминание перед `make clean`.

### 1.5. Хедер весит больше, чем весь код сайта

Живой браузерный трейс (`performance.getEntriesByType('resource')`), холодный кэш:

| страница | JS | CSS | изображения в критическом пути |
|---|---|---|---|
| index.html | 57 КБ | 35 КБ | **≈5 131 КБ** |
| schreiben.html | 119 КБ | 59 КБ | **≈5 902 КБ** |
| pipeline.html | 35 КБ | 22 КБ | **≈4 492 КБ** |

Из них общий хедер — 4 492 КБ на мобильной ширине и **6 580 КБ** на десктопе.
Проверено независимо, размеры файлов: `header-wash-mobile.png` 2.41 МБ,
`header-wash-desktop.png` 2.33 МБ, `header-flourish-right.png` 2.12 МБ,

около 180 px. Причём §4 CRITICAL-LINKS уже предписывает lossless-оптимизацию —
она просто не выполнена. Обрезать canvas до реально видимой области плюс
`oxipng`/`pngquant` снимет большую часть без единого риска для альфы.

Сжатие текста (gzip) уже включено в этом заходе — см. «Сделано».

### 1.6. Клавиатура не управляет личным списком

`js/wb-page.js:183-190` — кнопка «добавить/убрать слово» это
`<span role="button" tabindex="0">`, вложенный **внутрь** `<button class="wb-row">`.
`delegate()` слушает только `'click'`; во всём `wb-page.js` ровно один
`keydown`-обработчик, и тот на Escape. Браузер не эмулирует click для
не-нативного `role="button"`, значит Enter и пробел не делают ничего.

Это единственный способ управлять личным списком на сайте, и с клавиатуры он
недоступен. Эталон уже есть в том же проекте: `site-header.js:16-18,166-168` —
аватар сделан правильно, с keydown на Enter/Space.

Там же рядом: три оверлея в `schreiben.js` (карточка слова, аннотация, версии) —
ни один не удерживает фокус, у `#wordCard` нет даже `role="dialog"`, а
`.versions-dialog` заявлен `aria-modal="true"`, но Escape не обрабатывает.

### 2.1. Тёмная тема существует наполовину

Проверено выполнением в браузере:

| страница | кнопка есть | `.theme-dim` меняет вид |
|---|---|---|
| index.html | да | да (`rgb(247,242,239)` → `rgb(27,27,31)`) |
| pipeline.html | да | да |
| **schreiben.html** | **да** | **нет** — `before === after`, правил `theme-dim` в `schreiben.css` ровно 0 |

`localStorage` пуст: тема не сохраняется вообще, любой переход между страницами
возвращает светлую. `site-header.css` не содержит ни одного правила `theme-dim`,
поэтому шапка не темнеет ни на одной странице.

⚠️ И более глубокая причина, которую надо решить до, а не после: **в тёмной теме
ломается сама акварель**. Шапка остаётся светлой полосой с рваным краем поверх
чёрного фона (её цвет несёт PNG, а не CSS — `headerBg: rgba(0,0,0,0)`), мазки под
словами выцветают и съедают контраст с белым текстом, кнопки «+» становятся самым
светлым элементом страницы. Ни одна CSS-переменная это не перекрасит: **цвет
запечён в пикселях**. Тёмная тема в таком визуальном языке — не настройка, а
второй комплект ассетов. Стоит решить осознанно: либо рисовать второй комплект,
либо убрать кнопку.

Защита от переоплаты подтверждена по коду: `claim()` берёт только
`status IN (raw, NULL)` с `attempts < 3` — `done`/`failed`/`skipped` физически
недостижимы без явного `requeue`.

Что осталось кривого:

- **195 «регистровых пар» — не омографы, а дубли.** У `Bauen`/`bauen`,
  `Drucken`/`drucken`, `Aussteigen`/`aussteigen` заглавная форма побайтово
  повторяет `ru` строчной, и у **166 из 195 совпадает ещё и `pos`**. Это не
  `Wählen`(сущ.)/`wählen`(глаг.), а дважды сгенерированный почти одинаковый
  ответ. Ломает саму посылку стратегии ранжирования из I0 («регистр = разное
  значение») — здесь разницы в значении нет. Всего регистровых коллизий 1 198,
  дубли — 16.3 % от них, zipf доходит до 4.81. Тест на это **уже написан**:
  `qa_cards.py::check()`, правило `case-twin-identical-ru`.
- **`repair_qa` — шестая фаза, которой нет в документации.** В коде
  `enrich.PHASES` шесть фаз, в §6a CRITICAL-LINKS описано пять. И она опаснее
  остальных: `qa_cards.py::_requeue --apply` идёт с `drop_card=True`, то есть
  удаляет карточку сразу, тогда как прочие repair-фазы намеренно берегут старую.
  При этом PLANS.md I1 сам фиксирует **36 % ложных срабатываний** на Haiku-прогоне
  (`Pascal`, `Einstein`, `listen`, `Jojo-Effekt` — законные слова). Сейчас от
  их удаления защищает только то, что оператор вычеркнул их руками; в коде такой
  защиты нет. На живой базе фаза отработала на 68 словах, и `Die`/`Mir` вернулись
  побайтово теми же — токены потрачены впустую, что подтверждает вывод пункта J.
- **RU→DE поиск: окно в 50 строк берётся до группировки по смыслу.**
  `search.py` берёт `MAX_LIMIT=50` строк, и только потом Python группирует их
  `_collapse_synonyms()`. 839 из 125 660 русских значений объединяют больше 9
  разных лемм, худший кластер — «грубый», 42 леммы. Сам по себе ни один кластер
  50 не превышает, но с триграммными соседями запас 8 строк. Структурный риск,
  эмпирически на живом Postgres не подтверждён.
- **`vocab.db` не открывается голым `mode=ro`** — стабильно `SQLITE_CANTOPEN`,
  нужен `&immutable=1`. Задевает `qa_cards.py` и любой скрипт, копирующий этот
  паттерн: он решит, что база повреждена.

### 2.7. Мелкое, но заметное пользователю

- **Открытая вкладка карточки схлопывается при вводе.** `wb-page.js:345-356` —
  `applyDraw` пересобирает `#app` целиком каждые 180 мс, `tabsHTML` всегда
  рендерит вкладки закрытыми. Уточняешь запрос, не трогая карточку, — открытая
  «Grammatik» молча закрывается.
- **`pipeline.js` и `enrich.js` не проверяют `response.ok`** (5 и 1 место).
  На 500 с телом `{"detail":...}` `.json()` успешно распарсится, и ops-панель
  покажет «данных нет» вместо «сервер упал» — ложный диагноз ровно в инструменте
  диагностики. Соседние `wb-page.js`, `schreiben-api.js`, `site-header.js`
  проверяют `.ok` везде.
- **Поиск не отменяет устаревшие ответы.** `wb-page.js:358` — `loadSearch` при
  резолве безусловно перезаписывает `state.results`, не сверяя, что запрос всё
  ещё тот же; AbortController не используется.
- **Ротация `MISTRAL_KEY_SECRET` ломает ключи молча.** `crypto.decrypt` при чужом
  секрете возвращает `None` (это намеренно), но `has_mistral_key` в
  `/api/auth/me:53` и в панели флота (`vocab/api.py:233`) считается как
  `bool(user.mistral_key_enc)` — то есть проверяет NOT NULL, а не расшифровку.
  После смены секрета UI у всех 17 аккаунтов продолжит показывать «ключ привязан».
- **Сессии чистятся только при старте контейнера.** `main.py:77-79` — разовый
  вызов в `on_startup`, без периодического таска (в отличие от
  `mirror.periodic_sync` строкой ниже), а рестартовать контейнеры проект сам себе
  запрещает во время обогащения.
- **9 слитых веток не удалены** ни локально, ни на origin. Ветка `pipeline` (+3 к
  main) существует **только** на этой машине — на origin её нет.

## 3. MCP-серверы

Проверено по официальным источникам, не по памяти. Полные команды и ссылки — в
разделе «Источники» ниже.

### Стоит подключить

| сервер | зачем именно здесь | риск |
|---|---|---|
| **Chrome DevTools MCP** (Google, официальный) | Единственный способ агенту «увидеть» страницу без сборщика: скриншоты, консоль, network, Lighthouse. Ровно этим я поймал мёртвую кнопку темы и вес хедера | Средний: контроль браузера. Снимается флагом `--isolated` (временный профиль) |
| **DBHub, Postgres в read-only** (Bytebase) | Проверять ранжирование `pg_trgm` и счётчики зеркала, не рискуя аккаунтами и эссе | Низкий **только** с отдельной read-only ролью в Postgres |
| **DBHub, SQLite в read-only** | Тот самый повторяющийся паттерн «сверить `COUNT(*)` в обеих БД» из PLANS.md. WAL безопасно допускает читателей при живом воркере | Низкий |
| **Context7** (Upstash) | Версионные доки FastAPI/Alembic/pytest — не полагаться на устаревшие сведения модели | Минимальный, только чтение внешних доков |

```bash
claude mcp add chrome-devtools -- npx chrome-devtools-mcp@latest --isolated
```

```bash
claude mcp add context7 -- npx -y @upstash/context7-mcp
```

Для DBHub сначала завести роль в Postgres, потом подключать — иначе смысл
read-only теряется:

```sql
CREATE ROLE readonly_mcp WITH LOGIN PASSWORD 'сильный-пароль';
GRANT CONNECT ON DATABASE wordlist TO readonly_mcp;
GRANT USAGE ON SCHEMA public TO readonly_mcp;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly_mcp;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO readonly_mcp;
```

```bash
claude mcp add pg-readonly -- npx -y @bytebase/dbhub@latest --transport stdio --readonly --dsn "postgresql://readonly_mcp:пароль@localhost:5432/wordlist?sslmode=disable"
```

⚠️ Точное написание флага `--readonly` и формат SQLite-DSN подтвердить не удалось
по самому README пакета (read-only режим как функция там заявлен дословно, флаг —
из вторичных источников). Перед использованием: `npx @bytebase/dbhub@latest --help`.

### Не стоит

| сервер | почему не здесь |
|---|---|
| **Figma Dev Mode MCP** | В проекте нет ни одного Figma-файла — макеты рождаются в коде. Серверу нечего отдавать |
| `@modelcontextprotocol/server-postgres` | **Заархивирован**, депрекейтед с июля 2025, официально «no security guarantees», задокументирован обход read-only через statement stacking (`COMMIT; DROP SCHEMA public CASCADE;`) |
| `mcp-server-sqlite` | Тот же архив, без патчей |
| Lighthouse / axe MCP отдельно | Дублируют Chrome DevTools MCP, в котором Lighthouse уже есть |
| Docker MCP | `make up`/`down` уже доступны через Bash. MCP добавляет канал с властью над volume — риск для живой БД без пропорциональной пользы |
| Sentry MCP | Observability-стека в проекте нет — подключать не к чему |
| Playwright MCP | Полезен, но у него задокументирован RCE-класс через `browser_run_code_unsafe` (issue #1495) и была CVE-2025-9611. Chrome DevTools MCP закрывает ту же потребность здесь |

## 5. Осознанно НЕ трогал

- **Светлую тему и визуальный язык.** Акварель, издательская типографика,
  спокойная сетка — это сильная сторона проекта, а не место для переделки.
  Замечания выше касаются тёмной темы и веса ассетов, не самого языка.
- **Ранжирование поиска.** Пункт 0i из PLANS.md («точное совпадение проигрывает
  алфавиту») на живом бэкенде **не воспроизводится**: запрос `Wirkung` отвечает
  `die Wirkung` первой строкой, композиты ниже. Гипотеза была из прототипа, до
  бэкенда она не дошла.
- **`MISTRAL_KEY_SECRET`.** Ротация сделает нерасшифровываемыми Mistral-ключи
  всех 17 аккаунтов — молча, без ошибки. Это отдельная операция с миграцией
  (расшифровать под старым, перешифровать под новым), а не правка.
- **`scripts/ralph/` и правку `.gitignore` под неё** — они появились в рабочем
  дереве во время аудита и не мои; не коммитил и не трогал.
- **Историю git.** `git filter-repo` по удалённой папке дизайн-системы (64 МБ)
  ломает существующие клоны и требует согласованного force-push. `git gc` —
  безопасен и вернёт большую часть 502 МБ, но это тоже решение владельца.
